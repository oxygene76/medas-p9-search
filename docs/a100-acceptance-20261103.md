### Throughput: decision of the project lead (2026-11-03)

- **The throughput stage counts as met after the addendum.** The FAIL is an error of the measurement method, not of
  the card. `bin/peak` without arguments measures each operation over five launches right after one warm-up launch,
  about 30 ms in all, so it measured the card at the base clock it had on coming from idle.
- Found by the project lead: an nvidia-smi log every 200 ms during `bin/peak` showed 765 MHz first and 1365–1410 MHz
  only after about 0.4 s. 765 / 1410 = 0.543, the measured ratio (54.2 %). FP32 ran at 1410 MHz afterwards (99 %).
- Addendum `throughput-warm`, same limit: first 5 s of double add, then every operation over at least 2 s, SM clock
  logged every 100 ms:
  - double add 4.867e12 ops/s (99.9 % of 4.873e12), double mul 4.866e12 ops/s (99.9 %);
  - SM clock 1410 MHz in all 20 samples of each window, clock event reasons 0x0.
- The FAIL stays in `SUMMARY.txt` and in this report.

### dcgm

- **First run (12:01, package 3bc752c):** dcgmi warned "CUDA_VISIBLE_DEVICES is set on dcgmi process … Failed to
  get hostengine environment variable". The script's evaluation (case-insensitive grep for "fail" in the whole
  output) counted that warning as a failure, with exit code 0. The project lead evaluated the raw output of this run
  by the README rule and documents that separately. Its `dcgm-r3.txt` was overwritten by the second run, so it is not
  in the results.
- **Second run (14:26, package 2c860b7):** dcgmi without CUDA_VISIBLE_DEVICES, the card chosen by its DCGM id from
  `dcgmi discovery -l` (GPU 1 = the A100's UUID). DCGM 4.7.1:
  - software, memory, diagnostic, pcie, memory_bandwidth, targeted_stress and targeted_power: Pass;
  - nvbandwidth: Skip.
  - The rule (exit 0, no failure) holds. The Skip is not a failure.

## Findings for what follows

- **`check.sh` names the wrong GPU in its header.** The check report's line "gpu: NVIDIA L40S, 580.178.04, 8.9"
  comes from `nvidia-smi --query-gpu=… | head -n 1`. nvidia-smi ignores CUDA_VISIBLE_DEVICES and lists the first
  card, the L40S.
  - The cases ran on the A100 (CUDA_VISIBLE_DEVICES = its UUID). Their times differ from the L40S check of the same
    package (`runs/l40s/check-p9prod-9a084ed.txt`):
    - deep-57: 14.5 s here against 33.1 s there;
    - prod: 0.69 s against 3.20 s;
    - chain: 0.38 s against 1.63 s.
  - The package stays unchanged (`docs/production-criteria.md`). For the production run the header line is
    therefore not evidence of the card. The run has to be started with `CUDA_VISIBLE_DEVICES` set to the A100's
    UUID, and the card is shown by `nvidia-smi` (the process on GPU 1) or by the times of the check.
- **Other processes on the GPUs.** `nvidia-smi.txt` (11:40) shows ollama on both GPUs, also on the A100 (12 MiB), and
  a python3 process on the L40S. They have to be stopped before the speed benchmark and the production run.
